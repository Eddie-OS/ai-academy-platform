## 二、A 段出口准则逐条自检

### 1. 从「立项」走到「案例归档」的完整正向流程可跑通，附每一步的接口调用记录

证据：`CourseLifecycleApiIntegrationTest.主流程从立项走到案例归档`（走真实 HTTP，不走 Service）。

```
POST /api/courses                                                              → OK
GET  /api/courses/6                                                            → OK
POST /api/courses/6/transitions                   START_DEVELOP                → OK
POST /api/courses/6/transitions                   START_DEVELOP                → OK   ← 课程开发状态子状态机
GET  /api/courses/6                                                            → OK
POST /api/courses/6/materials                                                  → OK
POST /api/courses/6/transitions                   ENTER_SELF_CHECK             → OK
PUT  /api/courses/6/selfcheck                                                  → OK
GET  /api/courses/6                                                            → OK
POST /api/courses/6/transitions                   SUBMIT_REVIEW                → OK   ← 同一事务里快照 V1 + 开第 1 轮评审
GET  /api/courses/6/reviews                                                    → OK
POST /api/course-reviews/2/conclusion                                          → OK   ← 结论=通过，驱动主状态到「试讲」
POST /api/courses/6/trials                                                     → OK
POST /api/courses/6/transitions                   START_TRIAL                  → OK
POST /api/course-trials/1/conclusion                                           → OK   ← 双结论=合格，驱动主状态到「发布」
POST /api/courses/6/transitions                   ENTER_PROMOTION              → OK
POST /api/courses/6/transitions                   MARK_QUALIFIED               → OK
POST /api/courses/6/transitions                   ARCHIVE_AFTER_CASE_PUBLISHED → OK
GET  /api/courses/6/state-logs                                                 → OK
```

流转日志里主状态的完整序列（倒序）：`案例归档 → 精品案例 → 推广 → 发布 → 试讲 → 评审决策 → 自检 → 开发 → 立项`，与需求 5.3.1 的正向主线逐个对上。测试同时断言了首次发布时间与有效期截止日在进入「发布」时写下（EX1）。

> `MARK_QUALIFIED` 的副作用 `CREATE_CASE`（课程达精品后建案例）登记在 `EffectDispatcher.DEFERRED` 的 D 段，本段只验证转换本身可执行。这一条由 `EffectCoverageTest` 兜住：副作用码要么有处理器、要么登记了归属阶段，两者都没有就红。

### 2. 评审后替换课件，历史评审记录仍指向旧版本（R7 验证）

证据：`CourseMaterialReviewIntegrationTest.多轮评审各自绑定各自的版本`、`.版本快照复制当时的文件清单`。

第 1 轮评审绑定 V1，结论「不通过·修改后重新评审」后替换课件并再次提交评审，产生 V2 与第 2 轮；回看第 1 轮，`boundVersionNo` 仍是 V1，版本文件清单仍是「初版课件.pptx」。测试还断言了自检结果随材料一起快照（CK4）。

### 3. 同一课程并发两次「提交评审」只产生一条轮次记录

证据：`CourseLifecycleApiIntegrationTest.并发提交评审只开一轮`（两个线程同时 POST 同一转换）。

| 断言 | 实测 |
|---|---|
| 恰好一次成功 | 1 |
| 另一次被明确拒绝 | 返回 `CONCURRENT_MODIFIED` / `ILLEGAL_TRANSITION` / `DUPLICATE_SUBMIT` 之一，不是 `INTERNAL_ERROR` |
| 评审记录条数 | 1 |
| 材料版本数 | 1 |

> 为什么要断言错误码而不只断言「只有一条」：靠数据库唯一约束兜住并发，结果也是只有一条，但运营看到的是一句系统异常。**两个共享账号、2–4 名运营并行录入下，这种双击是日常而不是极端情况**（决策 AC1）。

### 4. 课程详情页的字段与需求文档第 9 章字段清单逐项对齐，附核对表

证据：`CourseFieldChecklistTest`（需求第 9 章 **64 项**逐项核对，核对表见本报告第四节）。

数据源是 `scripts/schema/extract-field-specs.mjs` 从需求文档机械解析出的 `requirement-fields.csv`，测试拿它对账手写的落点登记表。漏登记字段、落点列名写错、需求删掉的字段还留着登记，三种情况都会让测试红。

### 5. 自检题库改一条题目文本后，已有课程的自检记录显示的仍是旧文本

证据：`CourseTrialSelfcheckScheduleIntegrationTest.题库改了文案，已勾选的历史记录仍显示当时那句话`（开发 6.3.9）。

配套的 `规则 CK5：题目停用后不计入完成度分母，但已有的勾选仍然看得到` 一并通过。

## 四、E2-6：状态硬编码门禁（把人工搜索换成机器检查）

阶段文档建议「第 3 项建议做成 CI 检查而不是人工搜索」。本段照做，且做了两侧。

### 后端 `StateLiteralGuardTest`

| 断言 | 覆盖范围 |
|---|---|
| 业务、聚合、common 与其余 platform 模块的源码里不出现状态值字面量 | 剥掉注释后检查字符串字面量；状态词表取自 `StateMachineCatalog.all()` |
| Mapper 的 SQL 文本里不出现状态值 | 单引号字面量单独检查——写在文本块里的 `record_state = '待录入结论'` 从 Java 语法看只是一个长字符串 |
| 状态机模块导出的状态常量与转换表一致 | 业务代码敢用常量代替字面量的前提 |

**白名单为空。** 首次运行发现 4 处违规，全部改掉而不是加白名单：

| 位置 | 原写法 | 改法 |
|---|---|---|
| `CourseReviewMapper.recordConclusion` | SQL 里 `record_state = '待录入结论'` | 改为 `#{expectedState}`，由 Service 从状态机的「（空）→ 建评审记录」转换取 |
| `CourseTrialMapper.recordConclusion` | 同上 | 同上，取自「（空）→ 新建试讲记录」 |
| `AttendanceImportHandler` | `Set.of("已开课", "已结束")` 与提示文案 | 引用 `TrainingStateMachines.SESSION_OPENED/FINISHED`，模板说明与错误文案由同一份常量拼出 |
| `TrainingFeedbackImportHandler` | `Set.of("已开课", "已结束", "已归档")` | 同上 |

> 后两处是阶段 1 的代码，改动只把字面量换成常量引用，导入的校验行为与错误文案一字未变（`ImportHandlerIntegrationTest`、`ImportTemplateColumnsTest` 全过）。

### 前端 `stateLiteralGuard.test.ts`（STK-1）

状态词表取自后端状态机测试用的同一份 `requirement-transitions.csv`，扫 `src` 下全部非测试源码。首次运行 15 处命中，剥掉注释后剩 5 处，逐条处置：

| 位置 | 原文案 | 改法 |
|---|---|---|
| `CourseFormModal` | 「课程已立项」 | 「课程已创建」——提示语不该复述状态名 |
| `CourseTransitionPanel` | 「没有待执行的动作」 | 「没有选中任何动作」（「待执行」是培训计划的状态值，属误伤，但改了更准确） |
| `CourseTransitionPanel` | 「课程开发已关闭」 | 「关闭原因已记录，课程开发状态已变更」 |
| `CourseSchedulePage` | 「已关闭、课程归档、案例归档的课程不再出现」 | 「走到终态的课程不再出现」 |
| `CourseSelfcheckTab` | 「自检完成度」 | 「检查项完成度」 |

唯一的白名单是 `StatusTag.tsx`：设计规范 2.10 的三组状态标签配色表，键必须是状态值本身，且它只做查表、认不出的取值直接不渲染。

## 七、留给人工验收的动作

自动化覆盖不到的只剩视觉与交互，建议按阶段文档第五章走一遍：

1. 打开课程列表 → 详情 → 状态地图 → 排期日历，确认 1440×900 下布局与设计规范一致（间距 4px 标尺、卡片圆角 12px、按钮 6px）。
2. 用查看账号登录，确认写入口整体不渲染（PMI-5），而不是渲染出来点了报 403。
3. 在状态地图上拖一门「评审决策」的课到「试讲」列，确认提示的是「请到评审记录页签录入结论」而不是直接改状态——录结论类动作要连业务字段一起写。
