## 二、B 段出口准则逐条自检

### 1. 从「登记需求」走到「归档」的正向流程可跑通，两个分流出口各走一遍，附接口调用记录

证据：`DemandLifecycleApiIntegrationTest.出口二主流程从登记走到归档`、`.出口一主流程`（走真实 HTTP，不走 Service）。

出口二（造工具需求开发）：

```
POST /api/demands                                                              → OK
GET  /api/demands/3                                                            → OK
POST /api/demands/3/transitions                       START_REVIEW             → OK
POST /api/demands/3/review-conclusion                                          → OK   ← 结论+出口+评审记录+两个状态同一事务
GET  /api/demands/3/reviews                                                    → OK
POST /api/demands/3/transitions                       INITIATE                 → OK
POST /api/demands/3/transitions                       ENQUEUE                  → OK
POST /api/demands/3/transitions                       START_DEVELOP            → OK
POST /api/demands/3/transitions                       GO_LIVE                  → OK   ← 写首次/最新上线时间
POST /api/demands/3/transitions                       START_OPTIMIZE           → OK   ← 优化次数 +1
POST /api/demands/3/transitions                       OPTIMIZE_GO_LIVE         → OK
POST /api/courses                                                              → OK

出口一（用现有工具输出解决方案）：

```
POST /api/demands                                                              → OK
POST /api/demands/2/transitions                       START_REVIEW             → OK
POST /api/demands/2/review-conclusion                                          → OK

流转日志里需求开发状态的完整序列（倒序）：`已上线 → 优化中 → 已上线 → 开发中 → 待开发 → 已立项`，与需求 5.2.4 的正向主线加一次优化回环逐个对上。同一条测试还断言了 **优化上线不重算首次上线时间**（E1：15.2 的需求处理周期取首次值，跟着最新一次走会让周期越优化越短）。

出口一那条另外断言了**两个出口的字段不串台**：出口一走完全程后 `devState` 与 `firstOnlineDate` 仍为空。这一条只有把流程串起来才验得到——单测里两组状态字段各自都是对的。

### 2. 录入评审结论一笔写完结论、出口、评审记录与状态，绕过它推状态被硬阻断

证据：`DemandReviewOutletIntegrationTest.需求 5.2.1 第 3 行…`、`.REQUIRE_OUTLET：绕过评审结论接口直接把状态推到「已评审」会被硬阻断`、`.需求 5.2.1 第 5 行：重新评审清空出口，但不动已经产生的下游状态`、`.多轮评审各自留档，第二轮不覆盖第一轮`。

「已评审但没有出口」的需求在列表的「当前处理状态」列上是一个永久空白，也没有任何动作能推进它——所以出口必填是在服务层硬阻断的，不是前端表单的必填星号。

### 3. 需求↔课程 N:N 双向可查、重复关联幂等、解除关联留痕

证据：`DemandCourseLinkIntegrationTest` 六条。

| 断言 | 规则 |
|---|---|
| 一次关联，两侧都查得到，两侧各留一条审计 | R4 |
| 重复关联静默成功，不产生第二行，也不重复记审计 | K2 |
| 改关联说明按修改留痕，记字段名与前后值 | 需求 5.12 |
| 解除关联是物理删除，历史只剩审计日志这一处 | 开发 6.3.1 |
| 课程可不关联需求，需求也可不衍生课程，列表「是否有关联」筛选据此工作 | R3 |
| 关联不存在的对象报 `NOT_FOUND`，不留下指向空对象的关联行 | — |

`DemandFieldChecklistTest.关联表按关联表建` 另外把**形态**也钉住了：`biz_demand` 上不许有 `course_id`、`biz_course` 上不许有 `demand_id`（R1），`rel_demand_course` 上不许有 `deleted` 列。前者一旦出现，一个需求就只能关联一门课且课程侧无法反查；后者一旦出现，「解除关联」会变成软删除，与审计日志两处记同一件事。

### 4. 需求详情页的字段与需求文档第 8 章字段清单逐项对齐，附核对表

证据：`DemandFieldChecklistTest`（需求第 8 章 **42 项**逐项核对，核对表见第四节）。

做法与 A 段相同：数据源是 `scripts/schema/extract-field-specs.mjs` 从需求文档机械解析出的 `requirement-fields.csv`，测试拿它对账手写的落点登记表。漏登记字段、落点列名写错、需求删掉的字段还留着登记，三种情况都会红。

### 5. 未验收通过不能归档（C9 硬阻断），验收可反复且轮次累加

证据：`DemandAcceptanceIntegrationTest` 七条，其中四条直接对应本准则：

| 断言 | 实测 |
|---|---|
| 交付后业务验收状态自动置「待验收」，交付时间只写一次 | 通过，两个状态机各留一条流转日志 |
| 未验收通过点归档 → `BIZ_RULE_VIOLATED`「该需求尚未业务验收通过」，状态与归档时间一起回滚 | 通过 |
| 验收通过后可归档，归档时间落库 | 通过 |
| 重新提交验收轮次 +1，两轮各自留档、后一轮不覆盖前一轮 | 通过 |

## 四、需求第 8 章字段核对表（42 项）

完整表由 `DemandFieldChecklistTest` 每次运行打印。汇总结论：

| 章节 | 项数 | 落点 |
|---|---|---|
| 8.3.1 基本信息 | 13 | 12 项落 `biz_demand` 列（含「提出人部门」快照列 `proposer_dept`）；「代理人」按 N19 已删除 |
| 8.3.2 评审信息 | 5 | 4 项落 `biz_demand`；评审会议纪要走通用附件表，`ref_field = review_minutes` |
| 8.3.3 分流与处理 | 9 | 7 项落 `biz_demand`（出口一 `solution_*`、出口二 `dev_*` 与三个上线字段）；解决方案附件走通用附件表；「复用工具名称」按 V1.2 已删除 |
| 8.3.4 交付、业务验收与归档 | 9 | 全部落 `biz_demand`。**交付使用标记与归档标记不是两个布尔**：需求 5.13 第 5 项把两者归为一个状态机「需求交付标记」，第 28、35 项落在 `delivery_mark` 一列的两个取值上 |
| 8.3.5 系统字段 | 6 | 4 项落 `biz_demand`；**灯色与停滞天数登记为阶段 3**（`aggregate/warning`，列表页已留出列位） |

清单之外另核三张表：

| 表 | 核的是什么 |
|---|---|
| `dtl_demand_review` | 多轮评审的历史列齐全（5.2.1 可反复评审）。主表只存最新一轮 |
| `dtl_demand_acceptance` | 多轮验收的历史列齐全（5.2.5 不设轮次上限） |
| `rel_demand_course` | 需求 8.4 的关联字段齐全，且是关联表而不是主表外键列（R1），没有 `deleted` 列 |

> **为什么把灯色与停滞天数留在核对表里而不是删掉。** 一张「全绿但少两行」的表比一张有两行写着阶段 3 待办的表更容易骗过验收——前者看不出少了什么。

## 六、留给人工验收的动作

自动化覆盖不到的只剩视觉与交互：

1. 打开需求列表 → 详情七页签 → 态势图，确认 1440×900 下布局与设计规范一致（间距 4px 标尺、卡片圆角 12px、按钮 6px）。
2. 用查看账号登录，确认写入口整体不渲染（PMI-5），而不是渲染出来点了报 403。
3. 在详情页点「录入评审结论」，确认弹窗里**分流出口是必填**，且提交后「分流与处理」页签立刻按出口切换到对应的一组字段。
4. 在「关联课程」页签关联一门课，到该课程详情的「关联需求」页签确认反向可见；解除关联后确认两侧同时消失。
