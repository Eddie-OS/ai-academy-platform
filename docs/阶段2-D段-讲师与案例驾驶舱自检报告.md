### 1. 从「课程标注达精品」走到「案例已上架」的正向流程可跑通，附接口调用记录

证据：`CaseLecturerLifecycleApiIntegrationTest.案例主流程从课程达精品走到已上架`（走真实 HTTP，不走 Service；互动那三步以**查看账号**发起，标 `*`）。

GET    /api/lecturers/102                                                    → OK   ← 没人评过分时平均分是 null，页面渲染「—」
PUT    /api/lecturers/102                                                    → OK   ← 培养状态改值走编辑接口，不是 /transitions
GET    /api/lecturers/102/teaching-records                                   → OK

流转日志是 `已上架 → 待审核 → 整理中 → 待整理`（需求 5.9），**四条，第一条是自动创建那次的「（空）→ 待整理」**。同一条测试还断言了讲师侧全段一次 `/transitions` 都没调用——培养状态与在池状态都不是状态机（TS1、C10），走的是普通编辑接口。

> **这条链最容易断在中间那一格。** 案例侧与课程侧各自的测试都绿，而「运营在课程上标了精品、案例列表里什么都没出现」只有把两个模块串起来才看得见。它跨了两个业务模块、一个副作用与一个事件，是本段唯一无法在单模块内验证的路径。

### 3. C9 的两处硬阻断在案例侧真的拦得住，且拦在服务层

证据：`CaseIntegrationTest` 两条 + 审核覆盖三条。

| 断言 | 性质 |
|---|---|
| 「整理中 → 已上架」在转换表里根本不存在，跳过审核直接上架被 C3 的默认拒绝挡下 | C9 硬阻断上半 |
| 绕过审核结论接口、直接推「录入审核结论=通过」时，`RECORD_CASE_AUDIT` 副作用当场拒绝 | C9 硬阻断下半 |
| 审核不记轮次：第二次审核直接覆盖第一次，不建历史记录 | C09 第 4 条 |
| 下架修改后再次审核通过，上架时间保持首次的值 | 需求 12.3 第 15 项 |
| 「上架前正文必填」**不做**硬校验：正文留空照样能存能上架 | C2 |

> **上半与下半必须都有。** 只靠转换表，`POST /api/cases/{id}/transitions` 带 `AUDIT_PASS` 就能把案例推上架而四个审核字段全空——转换表允许「待审核 → 已上架」，它拦不住「没填审核人」。副作用侧的复核才是那道真正的门。反过来只靠副作用，「整理中 → 已上架」这条路会被放行。
>
> **最后一条与前四条方向相反，别把它一起「补严」。** 一期首要用途是补录已经发生的案例，几年前的案例不会有人回头补正文。

> **把培养状态做成状态机会在「改错了想改回去」时拦住运营，而这个限制从未被要求过。** 判断依据很简单：需求第 5 章里有它的转换表吗？没有。

> **授课记录改成实时派生（M-1）。** 需求 10.5 说场次转「已结束」时自动生成授课记录，但那一刻签到还没导入——「结束」派生的正是一条「签到导入」任务，此时落库的实际参训人数必然是 0，而后续导入签到不会回头改它。

### 5. 互动全部不去重、防刷静默丢弃、报告一经编辑转手动

证据：`CaseInteractionIntegrationTest` 十二条。

| 断言 | 规则 |
|---|---|
| 浏览不去重，同一账号打开三次就是三次 | 需求 12.4 |
| 点赞不去重、不可取消，同一账号点两次记两次 | 需求 12.4 |
| 同一 IP 一分钟内第 6 次点赞被**静默丢弃**——返回 false，不抛异常 | 需求 12.4 |
| 单次停留时长超过 30 分钟按 30 分钟计 | 需求 12.4 |
| 时长为 0 或负数一律不落库 | 避免 0 秒记录把平均阅读时长拉低 |
| 案例已删或记录已报过时静默返回，不给页面卸载请求留一片红 | — |
| 评论署名留空落 `null`，不写死「匿名」 | 需求 12.4 |
| 评论逻辑删除后不计入评论数，也不再出现在列表里 | 需求 12.3 第 19 项 |
| 自动生成的报告含三个段落，区间内的案例活动逐项计入 | 需求 12.6 |
| 区间内没有数据时计数写 0，而平均分写「—」 | 设计规范 3.3 |
| 报告一经编辑，生成方式转为「手动编辑」 | 需求 12.6 |
| 统计区间倒过来时当场拒绝 | 否则四段全是 0，报告看起来完全正常 |

> **这一组规则是 V1.2 按共享账号模型重写的重灾区，读起来全都「不合理」。** 凡依赖个人身份的去重都取消了：系统不知道点赞的是谁，「同一人只能赞一次」无法实现。浏览次数的含义因此是「被打开了多少次」而不是「多少人看过」——这一点在页面上也照实写了。
>
> **报告的生成方式必须跟着编辑走。** 读报告的人有权知道眼前的数字还是不是系统口径。允许运营手选生成方式，等于允许一份从没被编辑过的报告被标成「手动编辑」，反之亦然。

### E2-3 展开：案例是全平台唯一一处用户账号能写的地方

前三段的权限断言都是「查看账号读全通、写全拒」。D 段要分三档，`CaseLecturerLifecycleApiIntegrationTest` 四条各管一档：

| 档 | 接口 | 结论 |
|---|---|---|
| 读 | 讲师与案例两侧 15 个 GET | 查看账号全 200（PMI-2） |
| **用户可写** | `POST /cases/{id}/likes`、`POST /cases/{id}/comments`、`PATCH /cases/{id}/views/{viewId}` | 查看账号 200，**且查库确认真的落了行、`account_type` 记的是 `USER`** |
| 仅运营 | 案例编辑、删除、录入审核结论、统一转换、**删评论**、报告生成、报告编辑；讲师入池、编辑、移出 | 全 403，且被拒的请求不留痕迹 |

> **只断言 200 不够。** 点赞防刷是静默丢弃（返回 `false` 而不报错），「返回 200 但没写库」与「真的写了」在响应体上看不出区别。这三条必须落到库里查一次。
>
> **删评论与点赞、评论只差一个注解取值**，是这一段最容易开错的一格。它不能跟着点赞评论一起对用户开放：共享账号下系统分不出「自己的评论」与「他人的」，开了就等于任何人都能删任何评论。
>
> **`ArchUnit` 与本类分工不同，缺一不可。** `ArchitectureRulesTest.e1_5_userWritableWhitelistStaysAtTwo` 在构建期把 `USER_ALLOWED` 锁在 `business.kase` 包内，管的是「白名单出现在哪」；本类管的是「白名单里装的是不是那三条」。注解贴对了包但贴错了方法，静态断言看不出来。

## 四、需求 10.3／12.3 字段核对表（41 项）

完整表由 `LecturerCaseFieldChecklistTest` 每次运行打印。汇总结论：

| 章节 | 项数 | 落点 |
|---|---|---|
| 10.3 讲师 | 16 | 13 项落 `biz_lecturer` 列；累计授课次数、累计授课人次、平均评分三项实时聚合，不落库 |
| 12.3 案例 | 25 | 17 项落 `biz_case` 列；四项互动计数实时聚合；案例附件与封面图走通用附件表；代理人（N19）与收藏数（N21）已删除 |

**这两章的「A 系统自动生成」比前几章多得多，而它们不都是同一回事。** 核对时分成三类：

| 类型 | 例子 | 处置 |
|---|---|---|
| 首次到达型事实 | 首次试讲合格时间、上架时间 | **建列**，由那一次转换写入 |
| 聚合型统计 | 累计授课次数、浏览次数、点赞量、评论数、累计阅读时长 | **不建列**，由明细表实时 COUNT／SUM |
| 附件 | 案例附件、封面图 | 走通用附件表，靠 `ref_field` 区分 |

清单之外另核四处（这四张表的 markdown 表格没有序号列，抽取脚本收不到，同 C 段 11.5／11.6 的做法）：

| 表 | 核的是什么 |
|---|---|
| `dtl_case_view` | 12.4 浏览记录五列，含 V1.2 新增的 `account_type`、`source_ip`、`duration_seconds` |
| `dtl_case_like` | 12.4 点赞记录四列 |
| `dtl_case_comment` | 12.4 评论六列，含 `signature` 与 `deleted` |
| `dtl_case_report` | 12.6 总结报告五列（S-6 的推导已由 `V2_004` 对齐需求正文） |

另有两条反向断言：

- **四项互动计数不许出现在 `biz_case` 上。** 建了计数器列就要在浏览、点赞、评论、删评论四条路径上各维护一次，漏一条的症状是页面上的数字比明细表数出来的少，而没有任何报错。
- **不许有 `dtl_case_favorite` 表，`biz_case` 上也不许有收藏数列。** 收藏随 N21 已删除——共享账号下没有个人身份，收藏夹无意义。

## 七、留给人工验收的动作

自动化覆盖不到的只剩视觉与交互：

1. 在课程工作台把一门推广中的课程标注达精品，**不刷新**切到案例驾驶舱，确认那条案例出现在流程第一档，且案例名与负责人取自课程。
2. 打开案例详情看完四个区块，切走再切回，确认停留时长有被回报（互动页签的平均阅读时长会变），且**同一条案例反复打开时浏览次数逐次加一**——这是设计上就不去重，不是 Bug。
3. 用查看账号登录，确认案例详情页上**点赞与评论按钮照常渲染**，而编辑、审核、状态动作、删评论四类入口整体不渲染（PMI-5）；再确认讲师驾驶舱下所有写入口都不渲染。
4. 打开一个还没有人评过分的讲师，确认平均评分显示「—」而不是 0.0；再打开试讲台账，确认列表能按课程与结论筛。
5. 生成一份总结报告，改一个字保存，确认列表里那一行的生成方式从「系统自动生成」变成「手动编辑」。
6. 确认 1440×900 下七个页面的布局与设计规范一致（间距 4px 标尺、卡片圆角 12px、按钮 6px），案例卡片流的封面缺图时有兜底。
