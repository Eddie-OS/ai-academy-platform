# E1-5 验收证据：全部写接口有权限注解，ArchUnit 断言通过

> 出口准则 E1-5（开发实施文档 8.5）：**全部写接口有权限注解，ArchUnit 断言通过。**

## 一、判权链路：一处判定，注解只负责声明

```
请求 → PermissionInterceptor（唯一判权点）
         ├─ 读方法（GET/HEAD/OPTIONS）→ 放行（纪律 PMI-2：一期读权限完全无差异）
         └─ 写方法（POST/PUT/PATCH/DELETE）
              ├─ 取 @WriteApi 的开放范围
              │    ├─ ANONYMOUS     → 放行（只有登录、登出）
              │    ├─ USER_ALLOWED  → 两个账号都放行（需求 6.2.5 的点赞与评论）
              │    └─ OPERATOR_ONLY → 仅运营账号
              └─ 没有 @WriteApi → 拒绝（PMI-1 默认拒绝）
```

三条设计选择，每条都对应一个具体的失效模式：

| 选择 | 替代方案 | 为什么不用替代方案 |
|---|---|---|
| 判权只在拦截器一处 | 在 Service 或 Controller 里各自判 | 判权散落之后，「用户账号能不能写」这个问题没有唯一答案，只能靠通读全部写方法来回答。规则 AR-7 因此把 `AccountType` 的可见性限制在 `app.security` 包内，ArchUnit 守着这条边界 |
| 开放范围用注解声明 | 在拦截器里维护路径白名单 | 白名单与接口分处两地，新增接口时忘记登记不会有任何提示；注解贴在方法上，漏了 ArchUnit 编译期就红 |
| 漏注解 = 拒绝 | 漏注解 = 按默认值（仅运营）放行 | 「默认放行给运营」看起来更省事，代价是漏注解**不会被发现**——功能是通的，只有权限矩阵悄悄少了一条。默认拒绝会让漏注解立刻表现为 403，且拦截器会打 ERROR 日志指出是代码缺陷 |

## 二、静态门禁：三条 ArchUnit 规则

`backend/app/src/test/java/com/aiacademy/architecture/ArchitectureRulesTest.java`

| 规则 | 断言内容 | 防的是什么 |
|---|---|---|
| `e1_5_everyWriteEndpointDeclaresAudience` | `..controller..` 下带写 `@RequestMapping` 的方法必须带 `@WriteApi` | 新增写接口时漏声明开放范围 |
| `e1_5_userWritableWhitelistStaysAtTwo` | `USER_ALLOWED` 只允许出现在案例模块 | 需求 6.2.5 给用户账号开的写权限只有点赞与评论两条。**这条规则的价值是让「扩大只读账号的写权限」变成一次显式的规则修改**，而不是某个人随手改了一个注解取值 |
| `e1_5_anonymousWritesOnlyForLogin` | `ANONYMOUS` 只允许出现在登录接口所在类 | 免登录写接口是攻击面，必须只有登录、登出两个 |

## 三、运行时校验：注解真的在参与判定

`backend/app/src/test/java/com/aiacademy/app/security/WriteApiPermissionTest.java`

静态断言管不到两件事：**注解是否真的被拦截器读了**，以及**漏注解时运行时到底怎么表现**。一条只在编译期成立的规则很容易变成装饰——注解贴满了，拦截器却从来没读它。因此这个测试从 Spring 容器里取实际注册的处理器，并真的发请求：

| 测试方法 | 断言 |
|---|---|
| `已注册的写接口全部带注解` | 从 `RequestMappingHandlerMapping` 遍历实际注册的写接口（不是扫 class 文件），逐个检查注解；同时断言扫到的接口数 ≥ 10，防止这条断言在空转 |
| `漏注解的写接口一律拒绝` | 测试上下文里注册一个**故意不带注解**的写接口，运营账号调用返回 403 且消息为「未声明写权限范围」。同时断言路由确实落到了那个方法上——不加这一条，路径写错也会得到同样的 403 |
| `用户可写档位真的放行` | 两个只差注解取值的接口：`USER_ALLOWED` 的查看账号能写，`OPERATOR_ONLY` 的被拒。**这是「注解参与判定」的直接证据** |
| `读接口对两个账号一致` | 查看账号读导入批次、人员台账、配置中心四个 Tab、meta 接口全部 200（纪律 PMI-2） |
| `写入不看数据归属` | 运营删除 `created_by` 是别人的附件必须成功（纪律 PMI-4：判权与数据归属无关，一期没有负责人判权） |

## 五、反向对照：摘掉一个注解，两道门同时变红

**只有正向通过不能证明门禁有效**——一条永远为真的断言与一条没写的断言表现一致。因此把 `ImportController.confirm`（导入确认写入）的 `@WriteApi` 临时删掉，重跑同一批测试：

    漏注解的接口在运行时会被 PermissionInterceptor 直接拒绝，补注解时请顺便确认

两点值得注意：

1. **静态与运行时两道门同时红**，且静态那条直接点出了文件与行号；
2. 失败信息里带着「补注解时请顺便确认需求 6.2 的权限矩阵里有对应的一条」——ArchUnit 的 `because` 子句是给**将来撞上这条规则的人**看的，写「违反了 E1-5」没用，写清下一步该做什么才有用。
