| 问题 | 症状 | 处理 |
|---|---|---|

| 失效的代理环境变量 | npm 与 docker pull 都报 `ECONNREFUSED 127.0.0.1:19828` | README 给出清除命令 |

### 关于构建目录重定向

这是本阶段唯一一处「为绕开环境限制而偏离默认约定」的改动，值得单独说明。

Gradle 交给测试进程的 classpath 会按系统 ANSI 代码页编码，路径里的中文随即损坏，
测试进程报 `ClassNotFoundException`。加 `-Dfile.encoding=UTF-8` 与 `-Dsun.jnu.encoding=UTF-8`
（守护进程与测试进程都加）**无效**。用一份复制到纯英文路径的仓库验证，同样的代码 13 条断言全部跑起来，
确认根因就是路径。

解法没有搬迁仓库：classpath 上出现的只有 build 目录（class 输出、resources、各模块 jar），
**源码目录不在 classpath 上**，所以只要构建输出落在纯 ASCII 路径即可。判定条件写在
`build.gradle.kts` 里——仓库路径是纯 ASCII 时这段重定向自动失效，回落到默认的 `build/`，
因此仓库迁到英文路径后无需改代码。生产构建在 Docker 容器内进行，路径本就是 ASCII，不受影响。

一个连带约束：末级目录必须仍叫 `build`。ArchUnit 的 `DoNotIncludeTests` 是按
`build/classes/java/test` 这个路径形状识别测试类的，改名会让它把断言自身当生产代码扫进来，
AR-7 立刻误报（断言本身要引用 `AccountType`）。这一点在实测中真的发生过。

## 生产部署缺陷：`.env` 里的 `$` 被 Docker Compose 插值

**症状：应用正常启动、健康检查通过、日志无任何异常，但两个账号都登录失败。**

根因是 BCrypt 哈希含 `$`，而 Docker Compose 会把 `.env` 值里的 `$xxx` 当变量插值。
`{bcrypt}$2a$10$XjGbCBU9H/NAgdf8...` 里的 `$XjGbCBU9H` 被替换成空串，容器内实际拿到的是：

```
{bcrypt}$2a$10/NAgdf8i1pnVO2dbrajPvUx1/F6819qDn8rQiKE.cwB2
```

Compose 确实在 stderr 打了 `The "XjGbCBU9H" variable is not set` 警告，但它混在几十行
正常输出里，且措辞完全不像「你的口令坏了」。

**为什么这个缺陷特别危险：** 它在共享账号模型下等价于全系统不可用，
而唯一的症状「登录失败」会把排查方向引向口令记错、Nginx 配置、会话 Cookie——
没有任何线索指向 `.env`。上线当天遇到它，会是一场毫无头绪的排查。

原有的启动自检没能拦住：它只检查 `{bcrypt}$2` 前缀，而这个前缀在残缺哈希里完好无损。

### 三处修复

1. **`.env`**：`$` 全部转义为 `$$`。容器内 `printenv` 已确认还原为完整的 68 字符哈希。
2. **`printPasswordHash`**：改为同时打印「原始哈希」与「`.env` 专用（`$` 已转义）」两行。
   工具直接产出可用在目标位置的形式，比在文档里叮嘱「记得转义」可靠得多。
3. **`SharedAccountCredentialsCheck`**：改为按完整 BCrypt 结构校验
   （`{bcrypt}$2[aby]?$\d{2}$` + 53 位 base64），并在报错信息里直接点出最可能的原因与修复动作。

**反向验证**（对应 E0-3 要求的「故意违规必须被拦下」）：把 `.env` 改回未转义形式重新拉起，
应用启动失败，日志给出——

```
Caused by: java.lang.IllegalStateException: 运营账号的口令哈希结构不完整，长度 58，
应为 68（{bcrypt} + $2a$10$ + 53 位）。最常见原因：.env 里的 $ 未转义，
被 Docker Compose 当成变量插值掉了。用 gradlew :app:printPasswordHash 输出的
「.env 专用」那一行重新填写
    at com.aiacademy.app.security.SharedAccountCredentialsCheck.verify(...:51)
```

恢复 `.env` 后三容器重回 healthy。

### 修正的两处偏差

**其一，表头字号原为 14px，规范要求 13px。** 根因是 AntD 5 的 Table 只有 `cellFontSize`
一个字号 Token，表头与单元格共用，而规范要求两者不同（表头 13px、单元格 14px）。
这一档只能在 CSS 层覆盖，写在 `tokens.css` 里并注明了原因。
改对之后表头高度自动落到规范的 44px（20px 行高 + 上下各 12px 内边距）。

**其二，24px 标题的行高原为 30.4px，规范要求 36px。** AntD 的标题行高默认按字号推算，
比规范紧一档。已把 `lineHeightHeading1～4` 逐档显式指定，并把行高写成 `36 / 24` 这种
「规范行高 / 字号」的形式而不是 `1.5`——设计规范附录 B.1 明确 VI 页的 6 档字号／行高组合
属于「完全保留、不做改动」的部分，写成小数会让后来人看不出它对应哪一档。

两处都补了断言，改回去会红。
