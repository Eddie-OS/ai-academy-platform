## 备份恢复演练（同属 E5-3）——2026-08-04 已实跑

环境：本地 `aiacademy-postgres-local`（PostgreSQL 15 容器），库里带压测数据（课程 10001、签到 20000、浏览 100000）。
步骤照 `scripts/backup.ps1` 的 BK1／BK2／BK3 逻辑逐条执行。

| 步骤 | 实测 | 结果 |
|---|---|---|
| BK1 `pg_dump -Fc` | 退出码 0，dump **1,367,605 字节** | 通过 |
| BK3 轻量校验 `pg_restore --list` | 可完整解析，**745 个对象条目** | 通过 |
| 空库 `pg_restore` | `createdb` + `pg_restore` 退出码均 0，无报错输出 | 通过 |
| 抽查行数一致（10 张表） | 逐表比对源库／恢复库：需求 1、课程 10001、讲师 1、培训计划 2、场次 2、案例 1、签到 20000、浏览 100000、附件 2、状态日志 0。**不一致的表 0 张** | 通过 |
| 结构完整 | `public` 表数 **49 = 49**；Flyway 最高版本 **5.001**；`calc_light` 函数存在（V-9 那次迁移在 dump 里） | 通过 |
| BK2 附件增量同步 | 源 39 个文件 / 210,890,665 字节。首次 `robocopy /MIR` 退出码 1（有拷贝），二次退出码 0（无拷贝）——增量语义成立 | 通过 |
| 附件字节保真抽查 | 最大文件 `attachment/course/202608/4_perf-courseware.zip`（200MB）源与备份 SHA256 **完全一致** | 通过 |
| 演练产物清理 | 临时库已 drop、dump 已删、临时备份目录已删 | 完成 |

> 行数比对不只是走个形式。恢复后「表都在但某张表空了」是 `pg_restore` 部分失败的典型表现，
> 而它的退出码可能仍是 0。这次特意挑了 10 万行的 `dtl_case_view` 与 2 万行的 `dtl_attendance`——
> 大表才看得出数据段有没有真的恢复。
>
> 附件那条也一样：`robocopy` 退出码 0～7 全是成功语义，光看退出码等于没看，
> 所以补了一次 200MB 文件的 SHA256 比对。
