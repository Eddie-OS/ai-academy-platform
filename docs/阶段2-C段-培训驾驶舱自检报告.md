## 二、C 段出口准则逐条自检

### 1. 从「建计划」走到「场次已归档 + 计划已完成」的正向流程可跑通，附接口调用记录

证据：`TrainingLifecycleApiIntegrationTest.培训主流程从建计划走到计划完成`（走真实 HTTP，不走 Service；签到与反馈两步也走导入中心的真实 multipart 接口）。

```
POST /api/training-plans                                                       → OK
GET  /api/training-plans/8                                                     → OK   ← 计划号 JH+年月+3 位流水
POST /api/training-plans/8/sessions                                            → OK   ← 场次号「计划号-01」，时长由起止时间算出
GET  /api/training-sessions/3                                                  → OK
GET  /api/training-plans/8                                                     → OK   ← 实际场次数 COUNT 得出
POST /api/training-plans/8/transitions       FIRST_SESSION_STARTED             → OK
POST /api/training-sessions/3/transitions    START                             → OK
POST /api/training-sessions/3/attendees                                        → OK
POST /api/training-sessions/3/transitions    FINISH                            → OK   ← 派生「签到导入」「培训归档」两个任务
POST /api/imports/attendance/uploads                                           → OK
POST /api/imports/QD20260801152842/confirmation                                → OK   ← 名单外的人自动补入
GET  /api/training-sessions/3/attendees                                        → OK
GET  /api/training-sessions/3                                                  → OK   ← 实际签到人数 = 2
PUT  /api/training-sessions/3/attendances/1                                    → OK   ← 单条改判后人数即时变 1
PUT  /api/training-sessions/3/archive                                          → OK
GET  /api/training-sessions/3/archive                                          → OK   ← 归档完成标记落时间戳
POST /api/training-sessions/3/transitions    ARCHIVE                           → OK
POST /api/imports/training-feedback/uploads                                    → OK
POST /api/imports/XF20260801152843/confirmation                                → OK
GET  /api/training-sessions/3/feedbacks/summary                                → OK   ← 平均 4.5，匿名 1 条
GET  /api/training-sessions/3/feedbacks?pageNum=1&pageSize=20                  → OK
PUT  /api/training-sessions/3/feedbacks/2/ops-remark                           → OK
POST /api/training-plans/8/transitions       ALL_SESSIONS_FINISHED             → OK   ← 写实际完成时间
GET  /api/training-plans/8                                                     → OK
GET  /api/training-plans/8/state-logs                                          → OK
GET  /api/training-sessions/3/state-logs                                       → OK
```

两条流转日志各记各的：计划侧 `已完成 → 执行中 → 待执行`（需求 5.7），场次侧 `已归档 → 已结束 → 已开课 → 待开课`（需求 5.8）。同一条测试还断言了**排了场次不会把计划自动推到「执行中」**——纪律 C1 要求状态一律手动变更，「顺手」联动是这条线上最容易被加上的东西，加了以后运营就无法记录「计划已建但场次全部延期」这种真实情况。

### 2. 排课三项校验按需求 11.4.1 的性质落地：两项硬阻断、一项提示不阻断

证据：`SchedulingValidationIntegrationTest` 十三条。

| 断言 | 性质 |
|---|---|
| 讲师培养状态不是「可上岗」→ 硬阻断，文案说清当前状态 | 校验一，C9 例外 |
| 阻断后不留残留数据（场次行与流转日志一起回滚） | C3 |
| 课程未到「发布」之后的三个主状态 → 硬阻断 | 校验二 |
| 同一讲师同一天时段重叠 → **只提示**，保存照常成功 | 校验三 |
| 首尾相接（9–12 与 12–15）不算冲突 | 边界 |
| 过期课程 → 只提示 | EX6 |
| 编辑改讲师、拖动改期都重新校验 | 落地要点第 2、3 条 |
| 排课下拉只列能排的（讲师限可上岗、课程限发布之后） | 落地要点第 4 条 |

> **把第三项做成阻断等于让系统替线下做判断。** 同一讲师一天讲两场是常见安排，而「9:00–12:00 与 11:00–14:00 冲突」这件事运营自己看得出来，需要的是提醒不是拒绝。

`TrainingLifecycleApiIntegrationTest.非法转换硬阻断` 另外把 C3 在 HTTP 层的表现钉住了：跳过「已开课」直接归档返回 `ILLEGAL_TRANSITION` + 409，`message` 里带当前状态，且被拒的转换只留下创建那一条日志。

### 3. 签到与名单：导入是唯一录入通道，名单外的人自动补入且可识别

证据：`AttendeeAndAttendanceIntegrationTest` 九条 + `ImportHandlerIntegrationTest` 签到那四条（阶段 1 已有，本段复用）+ 端到端那条。

| 断言 | 规则 |
|---|---|
| 手工添加记「运营指派」，姓名与部门取台账当时的值做快照 | 11.5.1 |
| 签到导入发现名单里没有这个人 → 自动补入并标「随签到导入自动加入」 | 14.4、验收 A8-6／A8-7 |
| 同一场次重复导入按工号覆盖，不产生第二行 | 14.4 |
| 名单左连签到：没有签到记录的人也要出现在列表里，页面显示「未导入」而不是「未签到」 | 11.5.2 |
| 移除名单行不删签到记录，实际参训人数不随名单变动 | — |
| 单条修改保留导入批次号，改过的行仍属原批次 | 11.5.3 |
| 签到状态只有两值，传「迟到」报 `PARAM_INVALID` | 议题 24 |

前端侧 `SessionAttendeesTab.test.tsx` 两条把「未导入」与「未签到」的区别钉在了界面上：签到还没导入时整列显示「未导入」并提示去导入中心，**不是把所有人标成未签到**——后者会让运营以为这场培训一个人都没来。

### 4. 培训 4 个页面的字段与需求文档第 11 章字段清单逐项对齐，附核对表

证据：`TrainingFieldChecklistTest` 五条（第 11 章有序号的三节共 **40 项**逐项核对，核对表见第四节）。

做法与 A／B 段相同：数据源是 `scripts/schema/extract-field-specs.mjs` 从需求文档机械解析出的 `requirement-fields.csv`。**培训侧比前两段多一步**：11.5.1、11.5.2、11.6 三张表的 markdown 表格没有序号列，抽取脚本按「# | 字段 | 类型」识别表格，收不到它们，因此改用显式列清单核（同 8.4 关联表的做法）。不核的话，这三张表就是第 11 章里唯一没人对过的部分，而签到记录恰恰是一期使用频率最高的导入目标。

### 5. 反馈只从导入进来、正文任何账号不可改，运营备注可反复改；多次导入是追加

证据：`TrainingFeedbackIntegrationTest` 八条。

| 断言 | 规则 |
|---|---|
| 工号留空即匿名，工号／姓名／部门三列一起为 NULL | E1-7 |
| 匿名反馈同样计入平均分，匿名只影响「能不能看出是谁写的」 | FB3 |
| 没有反馈时平均分是「—」而不是 0 分 | 设计规范 3.3 |
| 同一场次多次导入是追加，不覆盖不去重 | FB4 |
| 反馈正文没有修改接口，运营备注可反复改并记备注时间 | FB1、11.7.2 第 10／11 项 |
| 改别的场次的反馈备注返回 404 | — |

界面上 `SessionFeedbackTab` 顶部固定挂一条「本场次已有 N 条反馈，再次导入将追加」的提示（规则 FB5）——反馈没有唯一键，这是运营发现自己重复上传同一份问卷的唯一机会。

> **E2-3 为什么按四类写接口分别拒一次。** 培训侧的写接口有四种形态：统一转换（`/transitions`）、对象表单（`POST /training-plans`、`DELETE /training-plans/{id}`）、名单维护（`/attendees`）、页签表单（`/archive`、`/ops-remark`）。漏给其中一类加 `@WriteApi` 不会有任何报错，只有针对那一类的请求会静悄悄地通过。

> **E2-6 在培训侧最容易破的一处是条件必填。** 需求 11.4 第 10、11 项要求「线下或混合时培训地点必填、线上或混合时线上链接必填」，照直写就是在前端表单里写死「线下」「混合」两个状态值。做法是后端 `TrainingEnums.forMetaApi()` 多下发两个键——「培训形式·需填培训地点」「培训形式·需填线上链接」，前端按下发的清单决定星号与必填校验（`TrainingSessionFormModal.test.tsx` 两条断言）。

## 四、需求第 11 章字段核对表（40 项）

完整表由 `TrainingFieldChecklistTest` 每次运行打印。汇总结论：

| 章节 | 项数 | 落点 |
|---|---|---|
| 11.3 培训计划 | 13 | 11 项落 `biz_training_plan` 列；「实际场次数」是下属场次的 COUNT，不落库；「代理人」按 N19 已删除 |
| 11.4 培训场次 | 16 | 15 项落 `biz_training_session` 列（第 7 项「开始时间 / 结束时间」一行占两列，`end_time` 由单独一条断言兜住）；「实际签到人数」是签到表的 COUNT，不落库 |
| 11.7.2 学员反馈 | 11 | 全部落 `dtl_training_feedback` 列。匿名时前三列写 NULL（E1-7） |

清单之外另核四处：

| 表／形态 | 核的是什么 |
|---|---|
| `dtl_session_attendee` | 11.5.1 参训名单七列齐全，含 `join_source`（撤销签到批次时靠它判断哪些名单行要一起回滚） |
| `dtl_attendance` | 11.5.2 签到记录九列齐全，含 `attend_time` 与 `dept_name_snapshot` |
| `dtl_training_archive` | 11.6 六列齐全。V2_003 起是**一场次一条归档记录**，不是一场次多行材料 |
| 归档附件形态 | 三类附件走通用附件表，靠 `ref_field` 区分；归档表上**不许有 `attachment_id` 单附件列**，留着它会让「多附件」这条需求悄悄退化成单附件 |

> **两个派生字段为什么不落库。** 实际场次数与实际签到人数落库就要在建场次、删场次、导签到、改签到、撤批次五条路径上各维护一次，漏一条的症状是页面上的数字比列表里数出来的少——而没有任何报错。规则 U2、C14 本来也要求实时计算。

## 六、留给人工验收的动作

自动化覆盖不到的只剩视觉与交互：

1. 打开培训排期日历 → 月／周视图切换 → 拖动一个场次改期，确认冲突提示是**弹窗提示而不是拒绝保存**，且刷新后日期已变。
2. 打开计划详情的「下属场次」页签新建一场，把培训形式在线下／线上／混合之间切换，确认**培训地点与线上链接的星号跟着变**，且提交时的必填校验与星号一致。
3. 打开一个已结束但还没导签到的场次，确认参训页签整列显示「未导入」并提示去导入中心，而不是显示一列「未签到」。
4. 用查看账号登录，确认四类写入口（状态动作、新建计划／场次、加参训人员、归档保存与运营备注）整体不渲染（PMI-5），而不是渲染出来点了报 403。
5. 确认 1440×900 下四个页面的布局与设计规范一致（间距 4px 标尺、卡片圆角 12px、按钮 6px）。
